## A. THE RELATIONSHIP WEB — render & resize

### A1. SVG web goes stale on window resize — no ResizeObserver — **High / Perf+Layout** — `index.html:12626` (`_render`), `13797` (resize listener)
**What's wrong.** Confirmed: zero `ResizeObserver` in the file. `_render()` reads
`web-svg-container.clientWidth/Height` and writes a fresh `viewBox` (12630-12633),
but it is only invoked by build, drag, pan, zoom, click, and filter-change — never
by a window/container resize. The single global resize listener (13797) is
`window.addEventListener('resize',Utils.debounce(()=>Render.chronicleBand(),200))`
— it redraws the chronicle band only. So when the user resizes the window, opens the
DevTools dock, rotates a tablet, or the panel itself reflows (the web lives in a
slide-in panel whose width can change), the SVG keeps its old `viewBox` and the
force-sim was laid out against the old `_svgW/_svgH` (700×500 defaults at 12499).
**Why it matters.** Tablet/laptop users who resize get a web that is offset, clipped,
or mis-scaled. The first `build()` runs before the panel has its real width if it is
called while the panel is animating in (transform/translateX) — `clientWidth` during
the slide can read a transient value, baking a wrong layout that never self-corrects.
**Better approach.** Attach a `ResizeObserver` to `#web-svg-container` in `init()`
(12741); on resize, debounce ~120ms, update `_svgW/_svgH`, and call `_render()` (cheap)
— and re-run a short `_runSim(30)` only if the dimensions changed materially so nodes
re-center. Also defer the first `build()` until the panel's `transitionend` fires, or
read dimensions inside a `requestAnimationFrame` after `.is-open` is applied.

### A2. Every drag/pan/zoom tick triggers a full `innerHTML` rebuild + listener re-bind — **High / Perf** — `index.html:12684`-`12720`, `12748`-`12781`
**What's wrong.** `_render()` rebuilds the entire SVG via `svg.innerHTML=edgeSvg+nodeSvg+labelSvg`
(12684), then re-queries `.web-node` and re-attaches `click` + `mousedown` listeners to
every node (12687-12712) AND re-attaches a background `click` listener to the svg every
single call (12715). `_render()` is called on every `mousemove` while dragging (12756),
every `mousemove` while panning (12763), and every `wheel` tick (12780). At up to 80
nodes that means: destroy/recreate ~80 nodes + ~N edges + N text labels as strings,
reparse them, and bind ~160 new listeners — dozens of times per second during a drag.
The repeated `svg.addEventListener('click',…)` at 12715 also **stacks duplicate
listeners** every render (it is never removed), so after a few hundred renders a single
background click fires hundreds of handlers.
**Why it matters.** Low-end laptops and tablets will drop frames and feel gluey while
dragging a node or panning; the leaked click listeners are an unbounded growth that
degrades the session the longer the panel stays open. This is the single worst perf
hotspot in the UI layer.
**Better approach.** Build the DOM once in `build()`; keep references to node/edge
elements. On drag/pan/zoom, mutate attributes only (`setAttribute('cx',…)`,
`setAttribute('transform',…)` on a single `<g>` group for pan/zoom). Use **one**
delegated `click`/`pointerdown` listener on the SVG (bound once in `init()`), reading
`evt.target.closest('.web-node')`. Pan/zoom should be a CSS/SVG transform on a wrapper
`<g>` — no per-node recompute at all. CROSS-REF L5 (the force-sim math itself) and L3
(event-plumbing of the leaked listener).

### A3. Web has no touch support — **Medium / UX+A11y (mobile/tablet)** — `index.html:12748`-`12781`
**What's wrong.** Drag, pan, and zoom are wired only to `mousemove`/`mousedown`/`mouseup`/`wheel`.
There are no `touchstart/touchmove` or `pointer*` handlers. The app explicitly supports
tablets (mobile gate threshold is 768px; sliders have `@media (hover:none)` fallbacks at
401-403). On a touchscreen the web is view-only — you cannot drag a node, pan, or pinch-zoom.
**Why it matters.** A tablet GM at the table (a core use case for a TTRPG tool) gets a
dead, immovable graph. The node-detail-on-click works (synthetic click fires on tap),
but exploration does not.
**Better approach.** Convert the handlers to Pointer Events (`pointerdown/move/up` with
`setPointerCapture`), which unifies mouse + touch + pen, and add a two-finger pinch for
zoom. This also fixes the `mouseleave`-only drag termination (12767), which never fires
on touch.

### A4. `click` vs `mousedown` drag conflict selects a node after every drag — **Low / UX** — `index.html:12688`, `12701`, `12715`
**What's wrong.** A node has both a `click` handler (toggles selection + detail, 12688)
and a `mousedown` handler that starts a drag (12701). A normal browser `click` fires
after mouseup even if the pointer moved (as long as it is on the same element), so after
dragging a node you almost always also toggle its selection/detail open or shut. There is
no drag-threshold or "did we actually move" guard.
**Why it matters.** Dragging to rearrange the web flickers the detail card and selection
state — feels buggy.
**Better approach.** Track pointer movement distance from `pointerdown`; if it exceeds a
few px, suppress the subsequent `click` (set a `_didDrag` flag, clear on next pointerdown).

## B. CSS PERFORMANCE / ANIMATION

### B1. Animated `filter:drop-shadow` keyframes force per-frame repaint — **High / Perf** — `index.html:221`-`225` (`ember-breathe`)
**What's wrong (acknowledged in brief, going deeper).** `@keyframes ember-breathe`
animates `filter:drop-shadow(...)` from 18px→24px blur on `.ember-glow-pulse`, applied
to the 140px stability hero number (`.wms-stab-num`, 373-374) and the chronicle "NOW"
dot (11654, 11675). Animating `filter` blur radius is a CPU-side repaint every frame —
the browser re-rasterizes the blurred layer continuously. It runs `infinite` at 4s, so
it never stops while the world shell is visible.
**Why it matters.** Constant low-grade CPU/GPU drain on the default ("ember") theme,
worse on integrated-GPU laptops and tablets — exactly Hunter's target hardware tier.
The hero number is huge (140px), so the rasterized region is large.
**Better approach (more beautiful + cheaper).** Pre-render the glow as a separate
absolutely-positioned `::after` layer carrying a *static* drop-shadow, then animate only
its `opacity` 0.4↔1.0 (compositor-only, no repaint). Same breathing effect, near-zero CPU.

### B2. Many concurrent infinite box-shadow/opacity animations on the ember dashboard — **Medium / Perf** — `index.html:229`-`257`, `266`-`275`
**What's wrong.** On the ember world shell the following can all run at once, infinitely:
two counter-rotating `ember-orbit` rings around the orb (234-246), up to three
`ember-pulse-bar` animations with `box-shadow` glows (250-257), the `ember-breathe`
hero (B1), the "NOW" dot pulse, and up to 9 `ember-particle` nodes rising on staggered
loops (266-275, spawned at 11646/11682). The pulse bars animate `opacity` (fine) but
carry a static `box-shadow` (cheap); the orbit rings rotate `transform` (compositor-OK).
The concern is the *aggregate*: 15+ infinite animations layered on one screen.
**Why it matters.** Combined with B1 this keeps the compositor and main thread busy
permanently on the default theme. Battery and fan noise on laptops.
**Better approach.** Honor `IntersectionObserver` / `document.hidden` to pause ambient
animations when the panel/tab is not visible; cap concurrent particles; the global
reduced-motion rule (B5) already lets motion-sensitive users escape, but the *default*
experience for everyone should be lighter. Consider pausing orbit rings when the orb is
off-screen (long chronicles scroll the left panel).

### B3. `.web-node`/`.web-edge` carry `transition:opacity .15s` but are destroyed every render — **Low / Perf** — `index.html:2274`, `2276`
**What's wrong.** `.web-node{transition:opacity .15s}` and `.web-edge{transition:opacity .15s}`.
Because `_render()` recreates these elements from scratch every frame (A2), the
transition never actually animates a value change — each element is brand-new with its
final opacity. The declared transition is dead weight and, worse, during selection
dimming it would (if elements persisted) animate, but here it just adds style-recalc cost
on freshly-inserted nodes.
**Why it matters.** Minor, but symptomatic of A2: the styling assumes persistent elements
while the JS throws them away. Fixing A2 (persistent DOM) makes this transition correct
and free.

### B4. Faction cards use `transform-style:preserve-3d` + heavy multi-shadow hover — **Low / Perf** — `index.html:475`-`478`
**What's wrong.** `.wms-fc{transform-style:preserve-3d}` with a hover that applies
`box-shadow:0 12px 36px rgba(0,0,0,.45),0 0 16px rgba(255,185,100,.08)`. `preserve-3d`
forces each card onto its own composited layer; large blurred shadows on hover are
repaint-heavy on the parent.
**Why it matters.** Minor jank on hover in a long faction grid. Acceptable but worth a
note if perf budget tightens.
**Better approach.** Drop `preserve-3d` unless a real 3D tilt is used; keep one shadow
layer; promote with `will-change:transform` only during the interaction, not statically.

### B5. Reduced-motion coverage is actually GOOD (positive finding) — `index.html:2137`-`2141`
**What's right.** The global rule `@media(prefers-reduced-motion:reduce){*,*::before,*::after{animation-duration:0ms!important;transition-duration:0ms!important}}`
plus the parallel `.force-reduced-motion *` rule (toggled by `applyMotionPref` at 13800,
gated on the `respectMotionPref` setting) is a belt-and-suspenders catch-all that kills
*all* animation/transition durations. This genuinely honors the preference everywhere,
including the ember ambient set. The per-class `.force-reduced-motion` rules (293-302 etc.)
are redundant with the wildcard but harmless.
**One caveat.** The wildcard zeroes *duration* but does not stop `infinite` animations
that have no transform endpoint dependency — for `ember-breathe` (B1) the duration:0
collapses it to its first keyframe, which is correct. Verified OK.

## C. LAYOUT ARCHITECTURE

### C1. `.world-mode-shell` is `position:absolute` divorced from `#app` grid, pinned by hardcoded `top` offsets — **Medium / Layout** — `index.html:345`-`346`, `2009`
**What's wrong.** `#app` is a CSS grid with rows `60px 1fr 140px` (1396-1397). The ember
world shell does NOT live in that grid — it is `position:absolute;top:60px;left:0;right:0;bottom:0`
(345), overlaying the grid with `z-index:2`. The `top:60px` is a hardcoded duplicate of
the grid's identity-strip row height. In GM mode a 36px toolbar row is inserted
(`grid-template-rows:60px 36px 1fr 140px`, 2002) and the shell's top is patched to
`top:96px` via `body.gm-mode .world-mode-shell` (2009). Three magic numbers (60, 36, 96)
must stay in sync by hand across CSS rules.
**Why it matters.** Any future change to the identity-strip height or GM toolbar height
silently misaligns the shell (gap or overlap under the header). Fragile and a known
maintenance trap. The `applyTheme` JS toggles `display:grid|none` on the same element
(13822) — so it is a grid container that is itself absolutely positioned, doubly indirect.
**Better approach.** Make the world shell a real grid item that occupies the `main`
(and, in GM mode, also clears the toolbar) area, the same way `.main-row` does, instead
of an absolute overlay. Then row-height changes propagate automatically and no `top`
offsets exist. If overlay semantics are needed, derive the offset from a single CSS
custom property (`--header-h`) referenced everywhere.

### C2. Copilot panel is a `position:fixed` overlay with NO backdrop and a low z-index — **Medium / Layout+UX** — `index.html:1800`-`1806`
**What's wrong.** `.copilot-panel{position:fixed;right:0;top:60px;bottom:0;width:420px;
z-index:calc(var(--z-sticky)+1)}` = z-index 11. It slides over the right side of the app
with no dimming backdrop and no scrim. Two consequences: (a) content behind it stays
fully interactive and visible, so clicks "leak" to the app underneath while the copilot
is open; (b) z-index 11 is far below modals (`--z-modal:1010`) and the SC slide-in panels
(`z-index:7000`, 1811) and tonight-mode (8000) — so if a modal or SC panel opens while
copilot is open, copilot is buried underneath but still occupies the right 420px with no
visual indication it is now behind. Its `top:60px` is again the hardcoded header height
and does NOT get patched in GM mode (unlike the world shell, C1) — so in GM mode the
copilot panel overlaps the 36px GM toolbar.
**Why it matters.** Stacking is inconsistent and the GM-mode top offset is a real
misalignment bug (copilot starts 36px too high, covering the toolbar). The no-backdrop
choice may be intentional (reference-while-typing), but then it needs focus management
(see D2).
**Better approach.** Adopt the same `--header-h`/GM-aware offset the world shell uses;
decide deliberately on modal-vs-non-modal (if non-modal, that is fine, but document it
and keep z-index above transient modals or below — not in an ambiguous middle).

### C3. Scrollbar is 4px wide — **Low / A11y+UX** — `index.html:1385`-`1387`
**What's wrong.** `::-webkit-scrollbar{width:4px;height:4px}` with a faint gold thumb.
4px is below comfortable hit targets and nearly invisible against parchment; Firefox
ignores it entirely (no `scrollbar-width`/`scrollbar-color` declared) so cross-browser
the scrollbar is inconsistent.
**Why it matters.** Hard to grab with a mouse, invisible to many users, and the many
`overflow-y:auto` panels (workbench, arsenal, wms-lp, wms-cp, sc-panel body) all rely on
scrolling. Motor-impaired users especially.
**Better approach.** 8-10px track, higher-contrast thumb, and add Firefox
`scrollbar-width:thin;scrollbar-color:` declarations.

## D. ACCESSIBILITY

### D1. Generic modals have NO focus trap and NO focus restore — **High / A11y** — `index.html:7084`-`7098` (open), `7459`-`7475` (close)
**What's wrong.** `Modals.open()` adds `.is-open`, hides body overflow, and auto-focuses
the first field (7098) — but it installs **no Tab focus trap**. There are ~25 modals
markedup `role="dialog" aria-modal="true"` (2755, 2801, 2831, 2874, 2904, 2964, 3097…),
yet `aria-modal="true"` is a *promise* to keyboard/AT users that focus is contained — and
it is not. A keyboard user can Tab straight out of any of these modals into the (now
visually hidden behind the backdrop, but still focusable) app behind it. Only ONE modal —
the frontend-design generator — implements a manual trap (9654-9657). Also, `close()`
(7459) never restores focus to the element that opened the modal, so keyboard focus jumps
to `<body>` on close. The mobile gate (4608) has the same gap: `aria-modal="true"` with
no trap and no `inert` on the background.
**Why it matters.** Screen-reader and keyboard-only users get lost behind the dialog;
this is a WCAG 2.4.3 (Focus Order) / 2.1.2 (No Keyboard Trap inverse) failure and makes
the dialogs effectively unusable without a mouse. RealmWright markets accessibility
implicitly via the reduced-motion work — this is the glaring gap.
**Better approach.** A shared `trapFocus(modalEl)` helper in `Modals.open` (cycle Tab
within focusable descendants, like the FD modal already does), store
`this._opener=document.activeElement` on open and `this._opener?.focus()` on close.
Apply `inert` (or `aria-hidden`) to `#app` while a modal is open so AT can't reach behind.

### D2. Copilot and SC slide-in panels have no focus management — **Medium / A11y** — `index.html:8065`-`8077` (Copilot), `1807`-`1822` (SC panels)
**What's wrong.** `Copilot.open()` (8065) just adds `.is-open` and focuses the input after
300ms; `close()` (8074) removes the class with no focus restore. The SC panels (sessions /
hooks / secrets / locations / bestiary / relations / web / threads, `.sc-panel`, 7000
z-index) are full slide-overs that present as dialogs but carry no `role`, no
`aria-modal`, no focus trap, and no focus restore. The web panel inside one of these is
where the relationship graph lives. Escape closes copilot/detail/modals (13147-13151) but
there is no Escape handler that closes the SC panels (only their X button, 4463/12798).
**Why it matters.** Keyboard users can't reliably escape these panels and focus is never
returned. Inconsistent with the modal pattern.
**Better approach.** Give SC panels `role="dialog"`, trap focus while open, add them to
the Escape chain at 13147, and restore focus on close. Same `trapFocus` helper as D1.

### D3. `detail-panel` declares `aria-modal="false"` but is treated as a dialog — **Low / A11y** — `index.html:2709`, `13149`
**What's wrong.** `<div class="detail-panel" role="dialog" aria-label="Event details" aria-modal="false">`.
It slides over content and Escape closes it (13149), but `aria-modal="false"` tells AT it
does NOT trap — which is honest (it doesn't), but then nothing manages focus into or out
of it either. It is a half-dialog: dialog role, non-modal, no focus handling.
**Why it matters.** Minor; AT users may not be moved into the panel when it opens.
**Better approach.** Either make it a true modal (trap + restore) or keep it non-modal but
move focus to the panel heading on open and back to the trigger on close.

### D4. Range sliders are `opacity:0` invisible overlays — affordance + a11y risk — **Medium / A11y+UX** — `index.html:392`-`403`
**What's wrong.** The world-shell stat sliders use a real `<input type=range>` but it is
`opacity:0` (393) sitting over a custom fill bar; the native thumb is only revealed on
`:hover`/`:focus-within` of the row (399), with a touch fallback at 401-403. The control
is genuinely a native range input (good for keyboard arrows and AT), but:
(a) on **pointer-capable desktop** the thumb is invisible until you hover the row — there
is no persistent visual indication the bar is draggable;
(b) I see no `aria-label`/`aria-valuetext` wiring in this CSS region (the input is styled
but the brief's `_renderSliders` builds it in JS — labels must be verified there; the
visible `.wms-sl-name` is a sibling `<div>`, not a `<label for>`), so a screen reader may
announce a bare slider with min/max but no name.
**Why it matters.** Discoverability for new users (invisible until hover) and AT users
(possible unnamed slider). Keyboard operation itself is fine (native input).
**Better approach.** Keep the thumb faintly visible at rest (e.g. opacity .5 → 1 on
hover/focus) so the affordance is always present; ensure each input has
`aria-label`/`aria-labelledby` pointing at its `.wms-sl-name` and an `aria-valuetext`
("72 of 100"). CROSS-REF L3 to confirm the JS sets these attributes.

### D5. Low-contrast secondary text on parchment — **Low / A11y (contrast)** — multiple (`--color-text-faint`, `web-legend` `#64748b`, `web-node-detail` `#94a3b8`)
**What's wrong.** Pervasive use of `--color-text-faint` and hardcoded slate greys
(`#64748b` on the web legend at 2267, `#94a3b8` on labels/detail at 2277/2288) for
metadata, captions, era labels, and the web legend. Against the dark web background
`#64748b` on `#06080d` is roughly 3.0:1 — under the 4.5:1 WCAG AA threshold for the small
9-11px text these are used at. The chronicle/era faint labels on parchment likely fail too.
**Why it matters.** Low-vision users and anyone in bright ambient light (a game table)
can't read the metadata. The text sizes are tiny (9-11px), which compounds it.
**Better approach.** Audit the faint palette against AA at the actual font sizes; lift the
legend/detail greys to ≥ `#9aa7ba`-ish on the dark surface, and bump tiny labels to ≥11px.

## E. RENDER EFFICIENCY

### E1. Full `innerHTML` rebuilds destroy scroll position and focus — **Medium / UX+Perf** — many sites (e.g. `6470`, `6518`, `6604`, `12684`, `11652`, `11676`)
**What's wrong.** The render layer rebuilds whole regions with `innerHTML=html` on any
`sc:changed` (the global `dispatchRender`→`Render.all()` path, 13784). Lists like the
workbench characters (6470/6491), arsenal (6518), nation card (6604), chronicle nodes
(11676), and the SC panels (12994-13001) are wholesale-replaced. Any element inside that
had focus (e.g. a partially-typed inline field) loses it, and scrollable lists jump back
to top. The web (A2) is the extreme case.
**Why it matters.** Editing one character and triggering a re-render can scroll a long
list back to top or steal focus mid-interaction — feels janky, hurts keyboard users most.
**Better approach.** Targeted updates (update the one changed row's text nodes) or, at
minimum, preserve and restore `scrollTop` + `document.activeElement` id around the
`innerHTML` swap. Long term, key the list items and diff. CROSS-REF L3 (the
`sc:changed`/`Render.all` fan-out decides how often these fire).

### E2. Layout read inside the chronicle resize path — minor thrash — **Low / Perf** — `index.html:6711`, `13797`
**What's wrong.** The resize listener (debounced 200ms) calls `Render.chronicleBand()`,
which reads `dotArea.clientWidth` (6711) then writes many absolutely-positioned dots —
read-then-write in the same frame. Debounced, so impact is small, but each call removes
all `.cb-dot` nodes (6707) and rebuilds them (full rebuild again).
**Why it matters.** Minor; only on resize. Bundled here for completeness.
**Better approach.** Already debounced — fine. If touched, batch reads before writes.

## TOP 3 — must fix

1. **A2 — Web full-rebuild + leaked listeners on every drag/pan/zoom tick** (`12684`-`12720`).
   The worst perf defect in the UI layer: 80 nodes re-stringified and ~160 listeners
   re-bound dozens of times per second, plus an unbounded background-click listener leak.
   Build the DOM once; mutate attributes; one delegated listener; pan/zoom via a `<g>`
   transform.

2. **D1 — Modals lie about `aria-modal` with no focus trap and no focus restore**
   (`7084`/`7459`). ~25 dialogs are keyboard/AT-broken. Add a shared `trapFocus` +
   opener-restore + `inert` background. (Also fixes the mobile gate, D2 panels.)

3. **A1 — Relationship web goes stale on resize (no ResizeObserver)** (`12626`/`13797`).
   Add a `ResizeObserver` on `#web-svg-container` that updates `_svgW/_svgH` and re-renders;
   defer the first build until the panel finishes sliding in so it doesn't bake a wrong
   layout from a transient width.

(Runner-up worth fixing with TOP 1: **B1** animated `drop-shadow` → animate opacity of a
pre-shadowed layer — cheap, default-theme-wide CPU win.)

### (A) CONFIRMED cross-refs — with code evidence + quantification

**A-R1 — CONFIRM L3#9.3 / brief item 1: the web re-renders on EVERY `sc:changed` regardless of field — and it is far worse than a "re-render": it is a full `build()` that RE-RANDOMIZES the layout, runs a 200-tick O(n²) sim, and WIPES pan/zoom + selection. — HIGH / Perf+UX — `index.html:13000`, `10883`, `12502-12581`.**
Traced the whole path:
- `setStat` (5545) dispatches `sc:changed{fields:['stat']}` on every slider **commit** (`change`, 6861).
- `dispatchRender` (12981): `['stat']` does not include `nation`, so no early return; control reaches the unconditional **`if(SHSPanels._open==='web')SHSPanels.renderWeb();`** at **13000** — it has NO field guard (unlike the per-entity branches at 12994-12999), so ANY field re-fires it.
- `SHSPanels.renderWeb()` (10883) → `RelationshipWeb.build(n)` (NOT `_render`) — the **full rebuild**.
- `build()` (12502) re-seeds every node to a circle + `(Math.random()-.5)*40` jitter (12564-65), sets `_selected=null` (12578), resets `_transform={x:0,y:0,scale:1}` (12579), then `_runSim(200)` (12580) — at the 80-node cap that is 80·79/2 = 3 160 pair-iterations × 200 ticks ≈ **632 000 distance computations**, followed by a full `_render()` innerHTML rebuild + listener re-bind (A2).

So R1-A2 understated the blast radius: I scoped A2 to drag/pan/zoom ticks, but the *real* trigger is the global `sc:changed` fan-out. Concretely: with the web panel open, **release a stat slider once → the entire graph springs back to a fresh random circle, the user's pan/zoom is gone, their selected node + detail card vanish, and 632k math ops run.** Same for adding a chronicle event, an AI apply, an undo, anything. This is a visible *correctness/UX* regression, not just jank. Confirms L3#9.3 and brief item 1; severity HIGH (L3 had it as a perf note; I raise it because of the layout/selection destruction).
**Fix:** the 13000 line must (a) be field-gated like its siblings (`if(fields.includes('relation')||fields.includes('character')||fields.includes('faction')||fields.includes('location'))`), and (b) call a cheap **`_render()`-only refresh when topology is unchanged**, reserving `build()` (re-sim + re-seed) for when nodes/edges actually changed. Preserve `_selected`/`_transform` across any refresh. This dovetails with Flow-R2's reconcile-step idea (see D-R2).

**A-R2 — CONFIRM L1#6 CSP `style-src 'unsafe-inline'` is forced by this layer. — Medium (architectural). — `index.html:43`, and pervasive inline `style=`.**
Verified: the codebase builds inline `style="width:${pct}%"` on every stat bar (6591/6594/6599), `p.style.cssText=...` on every spawned ember particle (11695), inline `style=` on the web detail card (12737), node sizing, etc. Removing `'unsafe-inline'` from `style-src` would break all of these. So L1's note is correct and L4-owned: the inline-style dependency is real and would need migrating to CSS custom properties (`style.setProperty('--w', pct)`) + class-driven rules before the CSP could be tightened. Lower priority than `script-src 'unsafe-inline'` (L1#6's main point) because style injection is far less dangerous than script, but it does block the hardening. Confirmed.

**A-R3 — CONFIRM L5#1 / L5#4 render sites are the inline `update()` fast-path, NOT `dispatchRender`. — `index.html:6592-6594` (trend arrow), `6835` + `6603` (breakdown sentence).**

### (D) CONSOLIDATED fixes (shared roots)

**D-R1 — ONE shared `withPreservedFocusScroll(el, rebuildFn)` + `trapFocus(modalEl)` + opener-restore helper closes A2-tail, B3, E1, C-R1, C-R2, C-R3, D1, D2, D3 at once.**
Two root causes underlie most of this lens:
- **Root 1: "render = destroy & rebuild DOM."** A2 (web innerHTML rebuild + listener leak), B3 (dead transitions on recreated nodes), E1 (innerHTML destroys focus/scroll), C-R1 (L3's fix regresses on it), C-R2 (inputs lose focus mid-type). The unifying fix is a single wrapper used by every render that does `el.innerHTML=…`:
  ```js
  function rebuildPreserving(el, html){
    const ae=document.activeElement, aid=ae&&el.contains(ae)?ae.id:null;
    const sel=aid&&'selectionStart'in ae?[ae.selectionStart,ae.selectionEnd]:null;
    const st=el.scrollTop;
    el.innerHTML=html;
    if(aid){const re=el.querySelector('#'+CSS.escape(aid)); if(re){re.focus(); if(sel&&'setSelectionRange'in re)re.setSelectionRange(sel[0],sel[1]);}}
    el.scrollTop=st;
  }
  ```
  This is the *pragmatic, no-rewrite* direction the brief asked for: it does NOT require a virtual DOM or rebuilding the app — it preserves caret + focus + scroll around the existing innerHTML swaps. For the **web specifically**, the equivalent is "don't `build()`, call `_render()` and keep `_selected`/`_transform`" (A-R1) — same principle (preserve interaction state across refresh), different mechanism (attribute mutation vs focus restore).
- **Root 2: "no shared focus-trap / focus-restore."** D1 (modals), D2 (copilot + SC panels), D3 (detail panel), C-R3 (mobile gate) are ALL the same missing `trapFocus(modalEl)` + `opener=document.activeElement` on open / `opener?.focus()` on close + `inert` the background. One helper, applied at `Modals.open/close`, `Copilot.open/close`, `SHSPanels.open/closeAll`, `MobileGate.show/hide`, and the detail panel. The FD-generator modal (9654) already has a working trap to copy.

**D-R2 — Render-architecture direction (no app rewrite) — dovetails with Flow-R2's reconcile-step idea.**
Flow-R2 (L3's consolidation) proposes routing all panel refresh through ONE place (dispatchRender's SHSPanels block) with a singular contract. That is the right hook for the perf/focus fixes:
1. **Field-gate line 13000** (web) like its siblings — it must NOT re-fire on unrelated `stat`/`chronicle` mutations (A-R1). This single line change kills the slider-drag-rebuilds-the-web pathology.
2. **Split web refresh into `_render()` (cheap, attribute-only, preserves pan/zoom/selection) vs `build()` (re-sim, only when topology changed).** `dispatchRender` calls `_render()`; only a `relation`/`character`/`faction`/`location` ADD/REMOVE calls `build()`.
3. **Wrap every panel `innerHTML=` in `rebuildPreserving`** (D-R1) so L3's early-return removal (its Finding 2.1 fix) becomes safe — this is the missing piece that makes L3's reconcile-step idea not regress focus.
